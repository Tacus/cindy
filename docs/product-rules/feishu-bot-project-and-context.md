# 飞书 / Lark 个人机器人：项目、角色规则与话题上下文

> **状态**：权威产品规则（authoritative）
> **适用范围**：Desktop 个人 IM 渠道中的飞书 / Lark 机器人，不是伙伴（Bot）或官方 hook
> **读取时机**：修改飞书 / Lark 机器人的项目绑定、角色 / 规则、AI 丰富，或任务定位、
> thread / topic 上下文与默认工作目录之前
> **产品裁决日期**：2026-10-13

## 1. 产品目标与边界

用户应能在 Cindy 设置里指定机器人工作的项目，预设角色与工作规则，并用 AI 优化自己
写下的草稿；在飞书话题里继续交流时，应自然接续这个话题的上下文，而不是把所有工作
塞进一个任务。

- 面向用户的 `session` 叫「任务」，任务里的交流过程叫「对话」，单条往来叫「消息」，
  遵守 [任务、对话、消息命名](task-and-conversation-naming.md)。
- 当前设置属于**本机当前 Cindy 账号的飞书 / Lark 个人 IM 渠道**，该账号连接的
  飞书与 Lark 机器人共用一份项目、角色与规则；不是每个机器人各自一份，也不自动同步
  到其他电脑或账号。修改设置不能影响其他 Cindy 账号。
- 项目绑定是 Agent 的默认工作目录和任务归组，不是文件访问沙箱。它不额外授予权限，
  也不保证 Agent 无法访问目录外的文件；权限确认仍遵守既有规则。用户无需在每条消息里
  重复报项目路径，但仅在消息里提及路径不等于修改渠道绑定。
- 这是通用渠道配置，不在 Core 中编码具体项目的工作流程；项目自己的说明、Skill 与
  Agent 能力仍按 [核心产品原则](core-product-principles.md) 分工。

## 2. 项目绑定与立即生效

1. 用户通过本机原生目录选择器绑定或更换目录。目录必须实际存在且是绝对路径；
   不要求一定是 Git 仓库。取消选择不改变绑定。
2. 未绑定时，新任务使用机器人自己的 Cindy 托管目录；绑定且目录可访问时，新任务
   使用绑定目录，并归入项目任务，而不是仍作为无项目对话展示。
3. 绑定、更换和解绑不能只影响以后新建的任务。仍跟随渠道默认目录的现有任务必须
   立即跟随变化；已被用户单独切到其他目录的任务不能被覆盖：

   | 操作 | 跟随变化的现有任务 | 变化后目录 |
   |---|---|---|
   | 首次绑定 / 更换绑定 | 仍在各自托管目录或上一绑定目录 | 新绑定目录 |
   | 解绑 | 仍在上一绑定目录 | 各自机器人的托管目录 |
   | 任意操作 | 已单独切到其他目录 | 保持原目录 |

4. 切换目录保留 Cindy 任务身份和可见消息历史，但停止旧的活动 Agent、清除旧目录的
   Agent 续接状态；下一条消息在新目录重建 Agent 上下文。**同一个 Cindy 任务不代表
   跨项目继续使用同一个底层 Agent 上下文**，不能把旧项目的执行状态带到新项目。
5. 绑定目录暂时不可访问时，设置页显示异常并保留原绑定；新任务回落托管目录，不能
   把不可访问的路径冒充正常项目。这个回落不意味着已有任务被自动迁移或绑定被清空。
6. 切换失败不能显示成功。目录选择、迁移与保存期间发生账号切换时，旧操作不得写入
   新账号，也不得操作新账号的任务；用户可以在当前账号重新执行操作。

## 3. 角色与规则

- 「角色」表达机器人身份、语气与工作定位；「规则」表达用户要求遵守的边界和习惯。
  二者独立、可选，每个字段最多 4000 字；清空字段即移除对应指令。
- 编辑自动保存，关闭设置面板不能丢失尚未保存的最新编辑；不要求用户再找一个保存按钮。
- 保存后的设置在下一次入站消息送给 Agent 时生效，不要求重建整个 Cindy 任务。
- 角色与规则是**主人预设的渠道指令**，不是本轮用户消息，也不是系统安全规则。模型
  输入必须标明这个来源；不得覆盖系统约束、扩大工具授权或伪装成本机直接命令。
- 注入的说明不得作为用户原文写入可见消息记录。来源口径遵守
  [消息来源](message-source.md)，不能只改模型输入、不交代来源。

## 4. AI 一键丰富 / 优化

1. 用户先写角色或规则草稿，再主动触发对应字段的 AI 丰富。空草稿不发请求；
   使用已有辅助模型链，不新增供应商选择，也不读取订阅凭证。
2. AI 保留用户原意与语言，改善结构、清晰度与可执行性；不能擅自增加身份、承诺、
   工作限制或权限。结果仍受单字段 4000 字上限约束，并允许用户继续修改。
3. 成功结果只更新所选字段并保存，不能用请求开始时的快照覆盖另一个字段或项目设置。
   等待期间若草稿已改变、面板已关闭或账号已切换，过期结果不能自动覆盖最新状态。
4. 模型不可用、请求失败或结果为空时，保留用户文本并给出可重试的错误，不能把字段
   清空，也不能把失败冒充保存成功。普通手动编辑不依赖辅助模型是否可用。

## 5. 新任务条件与上下文连续性

**项目回答「在哪里工作」，thread / topic 回答「接续哪一份上下文」；两者不能混为一谈。**
同一个项目可以有多个独立任务，绑定项目不能把不同话题折叠进同一个任务。

| 入站场景 | 任务与上下文规则 |
|---|---|
| 同一机器人、同一群、同一 thread / topic 内继续发消息 | 续同一个 Cindy 任务，共享该话题的上下文 |
| 同一群里新开不同 thread / topic | 使用不同 Cindy 任务，不能带入另一个话题的对话上下文 |
| 不同群，或不同机器人 | 即使目录相同，也不复用同一渠道任务 |
| 私聊 | 按机器人与私聊用户续接既有任务，与群及群话题隔离；不因普通回复新建任务 |
| 群主流中的一次新触发 | 正常路径先创建新话题，再进入该话题的独立任务，不挤进已有话题 |

- 上述话题规则适用于已经通过现有授权门的入站消息，不改变群里谁可以触发机器人，
  也不把话题上下文等同于开放给任意成员的共享任务授权。
- 路由身份必须跨重启稳定。不能只因重连或重启新建任务、丢失既有话题上下文；
  归档后继续交流的恢复行为沿用已有任务规则。
- 用户显式执行新建 / 重置任务、接管已有任务或切换项目时，遵守该操作的既有语义。
  特别是目录切换按第 2 节重建 Agent 上下文，不以话题连续性为理由续接旧项目。
- **允许的传输降级**：群主流触发时若创建话题失败，可沿用既有群主流任务。此时没有
  成功创建新话题，不能声称已经获得独立的话题任务；已经识别出 thread 的消息不能
  随意降级成群主流，更不能被路由到其他 thread。
- 不在本规则中另造超时、消息条数或日期分割条件；新增自动拆分条件需单独明确产品
  裁决，不能破坏同一话题内继续交流的默认语义。

## 6. 验收与依据

- 绑定目录后，从私聊及两个不同话题发消息：均在绑定项目工作；两个话题仍对应不同
  任务。回到第一个话题追问时能接续它自己的上下文，而不混入第二个话题内容。
- 重启连接后在原话题继续发消息，仍进入原任务；新开话题产生新任务。
- 更换 / 解绑项目后，默认任务目录与归组立即更新，任务历史仍可见，下一条消息不续接
  旧目录的 Agent；单独指定其他目录的任务保持不变。
- 绑定目录不可用时显示异常，新增任务使用托管目录；取消目录选择不修改现有设置。
- 修改角色或规则后下一条消息生效，原始消息里不出现注入说明；两个字段清空后不注入。
- AI 丰富失败保留原文；等待期间修改任一字段不会被旧结果覆盖；账号切换不会把旧账号
  的绑定、草稿或迁移写入新账号。
- 设置 UI 同时实现 Light / Dark，颜色使用语义 token；没有实际目检的模式必须如实
  标记未验证，不能把静态测试当成实机验收。
